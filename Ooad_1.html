📁 Pillar 1: Things (UML Vocabulary)

Things are the primary architectural abstractions and first-class citizens used to populate system blueprints. They represent the static nouns, dynamic verbs, organizational units, and explanatory context of a design model.

Structural Things

Static nouns modeling conceptual or physical layouts.

  • Class: Set of objects sharing attributes and operations.
  • Interface: Non-implemented public service contract.
  • Use Case: Sequence of goal-driven system actions.
  • Component: Modular, physical execution block.
  • Node: Computational hardware environment.
  • Collaboration: Cooperative pattern of roles.
  • Active Class: Class owning concurrent threads.
  • Artifact: Physical file (e.g., jar, dll) deployed to a Node.

Behavioral Things

Dynamic verbs representing pathways and state shifts.

  • Interaction: Chronological messages passed among lifelines.
  • State Machine: Specification tracking an object's discrete transitions over time.

Grouping & Annotational

Modularity containers and descriptive remark units.

  • Package: Organizational mechanism to build distinct namespaces.
  • Note: Visually attached textual comments or constraints.

🔗 Pillar 2: Relationships (The Connectors)

Relationships act as the semantic links in UML, connecting individual vocabulary elements to construct meaningful architectures.

Relationship Type Semantic Meaning Graphical Notation Sketch
Dependency A temporary "uses" relation. Changes to the supplier alter the client. [Client] - - - - - - - - - - > [Supplier]
Association A persistent structural link. One object holds a long-term field reference to another. [Class A] ----------------------- [Class B]
Aggregation A weak whole-part "has-a" relationship; lifetimes are independent. [Container] <>------------------ [Part]
Composition A strong parent-child "part-of" relationship; lifetimes are tightly bound. [Container] <#>----------------- [Part]
Generalization Static "is-a" inheritance. The subclass inherits parent attributes and methods. [Subclass] ----------------------|> [Superclass]
Realization Contract implementation. A concrete class executes the signatures of an interface. [Class] - - - - - - - - - - - - -|> [Interface]

📊 Pillar 3: Diagrams (The Visual Projections)

UML 2.5 defines exactly 14 official diagrams to represent static blueprints and dynamic operational system flows.

Structural Diagrams (7)

Focus on static structure independent of timeline-ordered execution.

  1. Class Diagram: Compile-time types and static relations.
  2. Object Diagram: SNAPSHOT of active instances at runtime.
  3. Package Diagram: System grouping schemas and folder modularity.
  4. Component Diagram: Physical modular elements and interface linkages.
  5. Deployment Diagram: Physical execution hardware mapping.
  6. Composite Structure: Decomposed classifier parts and runtime ports.
  7. Profile Diagram: Custom domain stereotypes and tagging schemas.

Behavioral Diagrams (7)

Focus on execution, processes, interactions, and state changes over time.

  1. Use Case Diagram: Actors, interactions, and system scope.
  2. Activity Diagram: Workflows modeling concurrent and parallel actions.
  3. State Machine: Event-driven lifecycle transitions of a classifier.
  4. Sequence Diagram: Chronological messages passed between lifelines.
  5. Communication: Structural layout emphasizing message flow path.
  6. Interaction Overview: Flowchart containing nested interaction loops.
  7. Timing Diagram: Focuses on precise state durations on time axes.

⚙️ Semantic Rules & Extensibility

Models achieve well-formedness by adhering to structural validation rules and incorporating standard extension properties.

Access Control Visibilities

Marker Visibility Level
+ Public: Visible to all classes.
- Private: Visible only inside the class.
# Protected: Accessible by derived subclasses.
~ Package: Accessible inside the same package.

Extensibility Framework

  • Stereotypes: Wrapped in guillemets <<stereotype>> to create custom vocabulary derived from base elements.
  • Tagged Values: Written inside braces {key = value} to append project metadata (author, version, target build).
  • Constraints: Set rules inside braces {rule} using natural language or Object Constraint Language (OCL).
Formal Multiplicity Boundaries:
M = { x ∈ Z | lower ≤ x ≤ upper }
Example limit constraint: {0 ≤ invoiceCount ≤ 10000}

💡 The Four Principles of Modeling

These core tenets dictate how software-intensive systems should be systematically analyzed, abstracted, and constructed.

Principle 1: Choice of Model Impact

The choice of what models to create has a profound influence on how a problem is attacked and how a solution is shaped. Algorithmic vs. Object-Oriented styles produce completely different visual worlds.

Principle 2: Flexible Precision

Every model may be expressed at different levels of precision. High-level maps align business stakeholders, while detailed specifications guide coders with exact attribute and signature details.

Principle 3: Grounded in Reality

The best models are connected to reality. Simplified abstractions must preserve direct traceability and mapping to concrete, compilable execution classes, databases, and physical architectures.

Principle 4: No Single Model is Sufficient

No single model is sufficient. Complex systems must be viewed through distinct, independent dimensions (e.g., the 5-View Architecture: Use Case, Design, Process, Implementation, and Deployment views).
