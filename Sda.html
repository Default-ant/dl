Software Design and Architecture Solutions

Module 1

Q) Discuss various process of Design process & phases and an example of any case study?

The software design process is a systematic series of steps that transform user requirements into a blueprint for constructing software. It bridges the gap between what the system needs to do (requirements) and how it will do it (implementation).

Phases of the Design Process:
  1. Requirements Understanding: Analyzing the SRS (Software Requirements Specification) to understand functional and non-functional needs.
  2. Architectural Design (High-Level Design): Defining the overall structure of the system, identifying main components (subsystems/modules), and their interactions.
  3. Detailed Design (Low-Level Design): Refining the architectural components into detailed data structures, algorithms, and class-level interfaces.
  4. Interface Design: Designing internal interfaces between modules and external interfaces (UI and APIs).
  5. Database/Data Design: Structuring the data models, schemas, and file systems.
Case Study Example: ATM System
  • Architectural Phase: The system is divided into a Client module (ATM machine interface), a Central Server module (transaction routing), and a Database module (Bank records).
  • Detailed Phase: The Client module is further designed into PIN verification algorithms, cash counting logic, and UI flow.
  • Interface Design: The UI screen flows for withdrawing cash are designed, alongside the network protocols for securely transmitting the PIN to the bank server.

Q) Explain about design viewpoints of software with a neat sketch diagram.

Software architecture is too complex to be represented by a single diagram. Viewpoints are used to represent the system from the perspective of different stakeholders (e.g., developers, users, system administrators). The most standard model is Kruchten’s "4+1" View Model.

  • Logical View: Focuses on functional requirements. Represents the object-oriented breakdown of the system (Classes, Objects, Packages). Stakeholders: End-users, Analysts.
  • Process View: Focuses on dynamic aspects, runtime behavior, concurrency, and performance. Stakeholders: System integrators, Developers.
  • Development View (Implementation View): Focuses on the static organization of software modules, libraries, and files in the development environment. Stakeholders: Programmers, Software Managers.
  • Physical View (Deployment View): Focuses on how software components are mapped to hardware infrastructure (servers, networks, topologies). Stakeholders: System Engineers, Operators.
  • +1 (Scenarios / Use Case View): This view ties the other four together by illustrating architectural decisions through a small set of important use cases.
[Logical View] <---> [Process View] \ / \ / [ +1 Use Cases] / \ / \ [Development View] <---> [Physical View]

Q) Explain how quality attributes are measured and assessed in a Software design Model?

Quality attributes (non-functional requirements) such as performance, security, reliability, and maintainability are crucial for software success. They are measured using specific metrics and assessed using structured evaluation methods.

Measurement (Metrics):
  • Performance: Measured via Response Time (milliseconds per request) and Throughput (transactions per second).
  • Reliability: Measured via MTBF (Mean Time Between Failures) and MTTR (Mean Time To Repair).
  • Maintainability: Measured via Cyclomatic Complexity (code paths), Lines of Code, and modular coupling/cohesion scores.
Assessment Methods:
  • ATAM (Architecture Tradeoff Analysis Method): A structured process for evaluating architectures against quality attributes. It involves identifying architectural approaches, creating quality attribute utility trees, and analyzing tradeoffs (e.g., higher security might lower performance).
  • CBAM (Cost Benefit Analysis Method): Builds on ATAM by adding economic analysis to the architectural decisions.
  • Simulation and Prototyping: Building vertical slices of the architecture to benchmark performance or security under load.
  • Expert Reviews: Peer reviews of design documents and UML models against known best practices.

Module 2

Q) Explain the basic principles of Jackson structured programming (JSP).

Jackson Structured Programming (JSP) is a method for structured programming developed by Michael A. Jackson. The core principle is that the structure of the program should match the structure of the data it processes.

Basic Principles:
  1. Data-Driven Structure: The design begins by analyzing and mapping the input data structures and output data structures.
  2. Three Fundamental Constructs: JSP uses only three basic structures to model data and programs:
    • Sequence: Execution of one part after another.
    • Iteration: Repetition of a part (loops).
    • Selection: Choosing between alternative parts (if-else).
  3. Tree Diagrams: Both data and program structures are represented using hierarchical tree diagrams.
  4. Merging Structures: The program structure is derived by merging the input data tree and the output data tree to find structural correspondences. Discrepancies between input and output structures are known as "structure clashes" (e.g., order clash, boundary clash) and are resolved using techniques like program inversion.

Q) Summarize the overall process of Jackson System development (JSD).

Jackson System Development (JSD) is an extension of JSP scaled up to entire system life-cycles. It is a linear process that focuses heavily on modeling the real-world domain before worrying about software functionality.

Overall Process (Three Main Stages):
  1. Modeling Stage (The "What"): The real-world entities (objects) that the system must interact with are identified along with the actions (events) they perform or experience in time sequence. These are modeled using entity structure diagrams.
  2. Network Stage (The "How"): The system is modeled as a network of communicating sequential processes. Each real-world entity from the modeling stage becomes a software process. New processes are added to handle input collection, output generation, and internal interactions. The communication happens via data streams or state vector inspections.
  3. Implementation Stage (The "Execution"): The conceptual network of concurrent processes is transformed into a practical, executable system on standard hardware. This involves scheduling processes, transforming data streams into standard I/O, and writing the procedural code (often using JSP principles).

Q) Describe the how stepwise and incremental strategy are used in Software design.

These two strategies are fundamental for managing complexity in software design.

  • Stepwise Refinement (Top-Down Design): Developed by Niklaus Wirth, this strategy starts with a high-level, abstract view of what the software must do. This major function is then repeatedly broken down (refined) into smaller, more detailed sub-functions. Each step adds more operational detail until the design is specific enough to be coded. It ensures that the overall architecture is sound before getting bogged down in low-level details.
  • Incremental Strategy (Bottom-Up or Iterative): Instead of designing the whole system at once, the system is designed, implemented, and delivered in small, usable pieces (increments). The first increment provides core functionality. Subsequent increments add new features or improve existing ones based on feedback. This allows for early delivery of value, easier testing of smaller components, and flexibility in adapting to changing requirements.

In practice, modern design often combines both: using stepwise refinement to structure an individual increment, while using an incremental approach to build the overall system over time.

Q) Discuss about the software designing involving SSADM in detail?

SSADM (Structured Systems Analysis and Design Method) is a traditional, rigorous, and highly document-driven waterfall method widely used in government and large enterprise systems.

Design in SSADM involves several strict stages:

  1. Feasibility Study & Requirements Analysis: Understanding the current system and defining the required business functions.
  2. Business System Options (BSO): Exploring different ways the system could be implemented (e.g., centralized vs. distributed) and choosing the best option.
  3. Logical Data Design: Creating detailed Entity-Relationship Diagrams (ERDs) and normalizing the data structures to the 3rd Normal Form (3NF).
  4. Logical Process Design: Using Data Flow Diagrams (DFDs) to map how data moves through the system, and Entity Life Histories (ELHs) to map how specific data entities change state over time.
  5. Physical Design: The logical models are translated into specific database schemas, hardware requirements, and physical program specifications. This phase defines the exact files, database tables, and batch/online processing routines.

Strengths: Highly rigorous, excellent documentation, minimizes risks in large teams. Weaknesses: Very slow, inflexible to changing requirements, can result in "analysis paralysis."

Q) Explain the use of structured analysis and design technique (SADT) for organizational design practices?

SADT (Structured Analysis and Design Technique) is a systems engineering methodology used for describing systems as a hierarchy of functions. It is highly effective for organizational design because it maps both automated software processes and human business workflows.

Key Uses in Organizational Design:
  • Top-Down Decomposition: SADT allows organizations to start with a high-level view of the enterprise (e.g., "Manufacture Product") and systematically break it down into sub-functions (e.g., "Procure Materials", "Assemble", "Ship").
  • ICOM Methodology: Every activity block in SADT is analyzed based on four arrows:
    • Inputs: Raw materials or data entering the process.
    • Controls: Rules, policies, or standards guiding the process (e.g., ISO standards, business rules).
    • Outputs: The finished product or processed data.
    • Mechanisms: The people, machines, or software systems performing the task.
  • Workflow Clarity: By mapping processes using SADT actigrams (activity diagrams) and datagrams (data diagrams), organizations can identify bottlenecks, redundant roles, and areas where automation can replace manual mechanisms.

Q) Summarize the key characteristics of component based design?

Component-Based Software Engineering (CBSE) or Component-Based Design (CBD) focuses on building software systems by composing pre-existing, reusable software components rather than writing everything from scratch.

Key Characteristics:
  • Reusability: Components are built once and used across multiple projects (e.g., a standard login module, a payment processing library).
  • Standardized Interfaces: Components interact exclusively through well-defined, published interfaces. The internal workings of the component are hidden (Encapsulation).
  • Independent Deployability: A component can be updated, replaced, or deployed independently without requiring the entire system to be recompiled, as long as the interface remains the same.
  • Composability: Components can be easily assembled and integrated (composed) to create complex applications.
  • Third-Party Assembly: Organizations can purchase Commercial Off-The-Shelf (COTS) components from third-party vendors and plug them into their architecture, saving development time and cost.

Q) Explain about the pipe and filter architecture style with real time examples?

The Pipe and Filter architecture style is a data-flow architecture where data is processed in discrete, independent steps.

  • Filters (Components): Independent entities that read a stream of input data, transform or process it, and produce a stream of output data. Filters do not know the identity of upstream or downstream components.
  • Pipes (Connectors): The conduits that route data streams from one filter to the next. They act as buffers and synchronize the data flow.
Advantages: High reusability, easy to add/remove filters, supports concurrent processing.

Real-Time Examples:
  • Unix/Linux Shell Commands: cat access.log | grep "ERROR" | sort | uniq -c. Here, commands like grep and sort are filters, and the | symbol represents the pipe.
  • Compilers: Lexical analysis (filter) → Token stream (pipe) → Syntax analysis (filter) → Abstract Syntax Tree (pipe) → Semantic analysis → Code generation.
  • Audio/Video Processing: Multimedia frameworks (like GStreamer) process raw video by passing it through noise-reduction filters, compression filters, and rendering filters via memory pipes.

Q) Explain the repository architecture style with an exemplary scenario?

The Repository (or Data-Centered) architecture style is built around a central data structure (the repository) and a collection of independent components that operate on that central data. The components interact through the repository rather than communicating directly with one another.

Exemplary Scenario: Modern Integrated Development Environment (IDE)
  • The Repository: The Abstract Syntax Tree (AST), symbol tables, and the source code files stored in memory.
  • The Independent Components:
    • Text Editor: Modifies the source code and updates the AST.
    • Compiler/Interpreter: Reads the AST to generate executable code.
    • Syntax Highlighter: Reads the AST to color-code variables and keywords on the UI.
    • Linter/Code Analyzer: Reads the AST to flag errors or stylistic issues.

Why it works here: If the editor communicates directly with the compiler, linter, and highlighter every time a key is pressed, the system becomes tightly coupled and unmanageable. With a repository, all components simply observe and react to changes in the central AST, ensuring loose coupling and data consistency.

Q) Discuss the layered architecture style and its main advantages?

The Layered Architecture (or n-tier architecture) organizes the system into a hierarchy of conceptual layers. Each layer provides services to the layer immediately above it and consumes services from the layer immediately below it. In a strict layered architecture, a layer cannot bypass the layer directly beneath it.

Common Tiers: Presentation Layer (UI) → Business Logic Layer → Data Access Layer → Database Layer.

Main Advantages:
  • Separation of Concerns: Different layers handle different responsibilities (e.g., UI designers can work on the presentation layer without touching database SQL).
  • Maintainability: Changes are localized. If you switch from an Oracle database to PostgreSQL, you only need to update the Data Access Layer; the Business and UI layers remain unaffected.
  • Reusability: Lower layers can be reused by multiple higher layers. For example, a single Business Logic layer can support a Web UI layer, a Mobile App UI layer, and an external API layer.
  • Testability: Layers can be easily mocked and tested in isolation.

Q) Discuss the main guidelines to consider and designing a user interface architecture. Design various user interface templates for online ticket booking application?

Main Guidelines for UI Architecture:

  • User-Centricity: Architecture must support the workflow of the end-user, minimizing cognitive load and keystrokes.
  • Consistency: Maintain consistent navigation, typography, and control behaviors across all screens.
  • Separation of UI from Logic (MVC/MVVM): Ensure the UI architecture is decoupled from business logic so interface changes don't break the backend.
  • Responsiveness and Feedback: The architecture must support asynchronous operations to keep the UI unblocked (e.g., showing a loading spinner while querying databases).
  • Accessibility (a11y): Design architectural support for screen readers, keyboard navigation, and high-contrast modes.

UI Templates for Online Ticket Booking Application:

  1. Home/Search Template: Contains the main branding, navigation bar, and a prominent search widget (Source, Destination, Date, Number of Passengers) with a "Search" call-to-action.
  2. Search Results Template: Displays a list/grid of available options (flights, buses, movies). Includes filtering/sorting sidebars (by price, duration, time) and summary cards for each option.
  3. Seat Selection Template: A graphical, interactive map of the layout (plane seating, theatre layout) allowing users to click available seats, with a real-time price calculator docked at the bottom.
  4. Passenger/User Details Template: A form-based template to collect names, contact info, and special requests. Includes form validation and error state displays.
  5. Payment & Checkout Template: A secure layout summarizing the itinerary and cost breakdown, accompanied by various payment gateway integrations (Credit Card, UPI, Wallets).
  6. Confirmation Template: A post-transaction screen displaying the PNR/Booking ID, QR code for scanning, and options to download or email the ticket.

Q) List out the various design rules for the user interface architecture.

The standard design rules for UI architecture are largely derived from Ben Shneiderman’s Eight Golden Rules of Interface Design:

  1. Strive for consistency: Consistent sequences of actions, identical terminology, and consistent color/layout should be used throughout.
  2. Enable frequent users to use shortcuts: Provide abbreviations, function keys, and hidden commands (like Ctrl+C/Ctrl+V) for expert users to increase pace of interaction.
  3. Offer informative feedback: For every operator action, there should be some system feedback (e.g., button click animation, success toast message).
  4. Design dialog to yield closure: Sequences of actions should be organized into groups with a beginning, middle, and end (e.g., checkout process with a clear "Success" final page).
  5. Offer simple error handling: Design the system so the user cannot make a serious error. If an error is made, the system should detect it and offer simple, comprehensible instructions for recovery.
  6. Permit easy reversal of actions: Features like "Undo" relieve anxiety and encourage exploration of unfamiliar options.
  7. Support internal locus of control: Make users the initiators of actions rather than the responders. Users should feel they are in charge of the system.
  8. Reduce short-term memory load: Keep displays simple, consolidate multiple pages, and do not force the user to remember information from one screen to the next.

Q) Explain the architecture structures used for shared information systems.

Shared information systems (like enterprise databases, cloud storage, or collaborative tools) require architectures that can handle multiple concurrent users while maintaining data consistency and integrity.

Key Architectural Structures:
  • Client-Server Architecture: The most common structure. Data is centralized on a powerful server (or server cluster), and multiple thin or thick clients request access. The server manages concurrency locks, transactions, and security policies.
  • Peer-to-Peer (P2P) Architecture: Data is distributed across all nodes in the network. There is no central server. Systems use consensus algorithms or distributed hash tables (DHT) to locate and share information. Useful for file sharing and blockchain.
  • Blackboard Architecture: Used for complex, non-deterministic problem-solving. A central "blackboard" holds the shared data state. Various independent "knowledge sources" (specialized modules) watch the blackboard and update it when they have new information (e.g., speech recognition systems).
  • Publish-Subscribe (Event-Driven) Architecture: Data producers (publishers) push information to an event bus or message broker. Consumers (subscribers) who are interested in that data receive it asynchronously. Excellent for real-time shared information (like stock tickers or chat apps).
  • Database-Centric / Shared-Nothing Architecture: In high-scale systems, the shared information structure uses sharding or replication (Shared-Nothing) where nodes have their own memory and disk, communicating only via high-speed networks to ensure high availability and partition tolerance (CAP theorem considerations).

Q) Describe architectural design patterns and their purpose.

Architectural Design Patterns are proven, reusable solutions to common, recurring problems in software architecture. Unlike lower-level software design patterns (like Gang of Four patterns which deal with class/object structures), architectural patterns dictate the high-level structural organization of the entire system.

Purpose:
  • Standardization: They provide a common vocabulary for developers. Saying "We are using an MVC architecture" instantly communicates the system's structure to other engineers.
  • Risk Reduction: Using battle-tested structures reduces the likelihood of catastrophic systemic failures regarding scalability, performance, or security.
  • Speed of Development: Patterns provide templates and guidelines, preventing teams from "reinventing the wheel."
  • Meeting Quality Attributes: Specific patterns are chosen to guarantee specific non-functional requirements. (e.g., Microservices pattern is chosen for high scalability and fault tolerance).

Q) Discuss common industrial applications of software architecture and design rules.

Software architecture principles are applied across various industries to meet highly specialized domain requirements:

  • E-commerce and Retail (e.g., Amazon): Utilizes Microservices Architecture. This allows different teams to independently scale and deploy the shopping cart, inventory management, and payment gateways without bringing down the entire store.
  • Automotive and Aerospace (e.g., Tesla, Boeing): Utilizes Real-Time and Embedded Architectures. Emphasizes strict timing constraints, fault-tolerance, and hardware redundancy to ensure critical systems (like brake deployment) never fail or lag.
  • Banking and Finance: Utilizes Event-Driven and Mainframe/Layered Architectures. Focuses heavily on ACID compliance for transactions, security layers, and high-throughput messaging (like Apache Kafka) for high-frequency trading.
  • Healthcare (e.g., Hospital Management Systems): Utilizes Secure Layered Architectures. The primary focus is on strict data privacy (HIPAA compliance), auditing, and interoperability standards (HL7/FHIR) between different medical sub-systems.

Q) Apply FACADE and decorator structural design patterns to online reservation systems.

These two Gang of Four structural design patterns can vastly improve the design of an online reservation system.

1. Applying the FACADE Pattern:

Problem: To book a ticket, the client UI might have to interact with the InventorySystem (to lock a seat), PaymentGateway (to process credit cards), and NotificationService (to send an SMS). This creates tight coupling and complex client code.

Solution: Create a ReservationFacade class. This class provides a single, simple method: bookTicket(userDetails, paymentDetails, seatId). Internally, the Facade handles the complex choreography of contacting Inventory, Payment, and Notification. The client UI only interacts with the Facade, shielding it from subsystem complexity.

2. Applying the DECORATOR Pattern:

Problem: A passenger can buy a basic ticket, or add various extras (Extra Luggage, Priority Boarding, In-Flight Meal, Insurance). Creating subclasses for every possible combination (e.g., TicketWithMealAndLuggage) causes a "class explosion."

Solution: Use Decorators to add features dynamically at runtime.
1. Create a base BasicTicket object that implements a Ticket interface with a getPrice() method.
2. Create decorator classes like MealDecorator and LuggageDecorator that wrap the base ticket.
3. When calculating the final price, the decorator calls the base getPrice() and adds its own fee.
Result: A single ticket object can be wrapped in multiple decorators at checkout dynamically, without altering the core BasicTicket class.
